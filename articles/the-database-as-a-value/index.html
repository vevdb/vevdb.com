The Database as a Value

In his 2012 Datomic talk The Database as a Value, Rich Hickey presented a simple idea: a database can be an immutable value. An application can hold several complete worlds at once: the present, last Tuesday, and the result of a transaction that has not happened. Any of them can be passed to the same function. VevDB brings that model to a small native component.

Andreas Flakstad September 15, 2026 5 minute read

Most application code receives an ID, a repository, or a connection. Every query therefore reaches into one particular world: whatever happens to be in the database now. The limitation becomes visible when the application needs to ask a different question. Would this permission change expose customer data? Who could access the production console last Tuesday? Can we preview the consequences before granting anything?

Applications often represent what-if state, historical state, previews, and tests separately, using staging tables, copied objects, audit logs, replay machinery, and repository mocks. Every representation must remain consistent with the same domain. An immutable database value offers another programming model.

Change the database value, not the function

Imagine an access-control editor. Before granting a team a new role, it must discover which systems become reachable and which security policies would be broken. Express that analysis as an ordinary function whose first argument is a database value:

// Pseudocode. Values in, values out.
function evaluateAccess(db, team):
  return {
    reachable:  query(db, resources_reachable_by(team)),
    violations: query(db, policies_broken_by(team))
  }

current  = database(connection)
past     = asOf(current, lastQuarter)

proposed = with(current, [
  grant(team: "Contractors", role: "Billing admin")
])

evaluateAccess(current,  team: "Contractors")  // what is
evaluateAccess(past,     team: "Contractors")  // what was
evaluateAccess(proposed, team: "Contractors")  // what could be

evaluateAccess does not know which world it received. It sees one complete database value. with produces a fully queryable successor value, so the application can keep both worlds, run the same rules against each, compare the outcomes, then discard the proposal or transact its facts.

An as-of value answers ordinary domain questions at a chosen point in time. A history view exposes assertions and retractions when the audit trail itself is the question. Both use the same underlying facts.

Current, historical, and hypothetical state share the same data model and query interface. Each can be passed directly into ordinary application functions, without a separate “preview mode.”

The whole database as input to a pure function

Functional core / imperative shell splits a program in two. A deterministic core decides what should happen. A thin shell owns I/O and makes it happen. The split becomes harder when the business logic needs database access. The core is then either starved of context, fed a carefully assembled object graph, or allowed to reach through a repository and perform I/O.

The shell can instead pass a stable view of the whole database into the pure function. The value is not a copy of all its data. The shell chooses a value, passes it to the core, then performs the returned transaction and effects:

// Functional core
function decide(db, command):
  if not allowed(db, command):
    return rejection

  facts = factsFor(command)
  nextDb = with(db, facts)
  effects = effectsFor(nextDb, command)

  return { facts, effects }

// Imperative shell
db = database(connection)
result = decide(db, command)

transact(connection, result.facts)
send(result.effects)

The core can query the complete database value, follow relationships, use rules, and derive exactly the view it needs without performing I/O or changing durable state. Tests need no repository mock. Pass decide a different value: a minimal fixture, last Tuesday’s database, or a proposed migration.

Where this model fits

This model fits applications that need to:

  • preview and compare proposed changes before committing them;
  • run today’s decision logic against historical state;
  • give pure functions and tests complete domain context.

For straightforward current-state rows and operational data such as caches, sessions, job state, and derived indexes, SQLite is usually simpler. VevDB includes a bundled SQLite API for that state. Distributed coordination belongs to another class of database.

The database value is the API

An application built around database values has one path for domain reasoning. The shell chooses a state, the core asks questions, and the connection commits facts. Current, historical, and hypothetical values all follow this path.

Datomic established this programming model. VevDB packages it as a native embedded component for self-contained desktop applications, developer tools, on-premises products, and small services. The current native SDK downloads are about 3–4 MB, including the query engine and bundled SQLite storage layer. In application code, current, historical, and hypothetical state all enter through the same interface: the database value.
