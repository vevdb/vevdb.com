The Database as a Value

In his 2012 Datomic talk The Database as a Value, Rich Hickey presented a deceptively simple idea: a database can be an immutable value. The consequence is striking. An application can hold several complete worlds at once. These can represent the present, last Tuesday, and the result of a transaction that has not happened. Any of them can be passed to the same function. VevDB brings that model to a small native component.

Andreas Flakstad September 15, 2026 5 minute read

Most application code receives an ID, a repository, or a connection. Every query therefore reaches into one particular world: whatever happens to be in the database now.

The limitation becomes visible when the application needs to ask a different question. Would this permission change expose customer data? Who could access the production console last Tuesday? Can we preview the consequences before granting anything?

What-if state, historical state, previews, and tests then acquire separate representations. Staging tables, copied objects, audit logs, replay machinery, and repository mocks. The hard part is no longer creating them. It is keeping all those representations faithful to the same domain.

There is another programming model: make the database itself an immutable value.

Change the database value, not the function

Imagine an access-control editor. Before granting a team a new role, it must discover which systems become reachable and which security policies would be broken. Express that analysis as an ordinary function whose first argument is a database value:

// Pseudocode. Values in, values out.
function evaluateAccess(db, team):
  return {
    reachable:  query(db, resources_reachable_by(team)),
    violations: query(db, policies_broken_by(team))
  }

current  = database(connection)
past     = asOf(current, lastQuarter)

proposed = with(current, [
  grant(team: "Contractors", role: "Billing admin")
])

evaluateAccess(current,  team: "Contractors")  // what is
evaluateAccess(past,     team: "Contractors")  // what was
evaluateAccess(proposed, team: "Contractors")  // what could be

evaluateAccess does not know which world it received. It sees one complete database value.

with produces a fully queryable successor value. Keep both worlds, run the same rules against each, compare the outcomes, then discard the proposal or transact its facts.

The useful shift is not merely that snapshots exist. It is that current, historical, and hypothetical state share the same data model and query interface. Application functions do not need a separate “preview mode.”

The whole database as input to a pure function

Functional core / imperative shell splits a program in two. A deterministic core decides what should happen. A thin shell owns I/O and makes it happen. The pattern is easy to recommend until the business logic needs the database. Then the core is either starved of context, fed a carefully assembled object graph, or allowed to reach through a repository and perform I/O.

A database value removes that tradeoff. Give the pure function a stable view of the whole database. It is not a copy of all its data. The shell chooses a value, passes it to the core, then performs the returned transaction and effects:

// Functional core
function decide(db, command):
  if not allowed(db, command):
    return rejection

  facts = factsFor(command)
  nextDb = with(db, facts)
  effects = effectsFor(nextDb, command)

  return { facts, effects }

// Imperative shell
db = database(connection)
result = decide(db, command)

transact(connection, result.facts)
send(result.effects)

The core does not have to be starved of context to stay pure. It can query the complete database value, follow relationships, use rules, and derive exactly the view it needs. Yet it still has no authority to change durable state.

Tests need no repository mock. Pass decide a different value: a minimal fixture, last Tuesday’s database, or a proposed migration.

Ask the past the same question

An audit log tells you what was written. The application usually needs to know what was true.

When earlier database states are themselves database values, the ordinary application query remains useful:

lastQuarter = asOf(current, quarterEnd)

report = evaluateAccess(
  lastQuarter,
  team: "Contractors"
)

A history view exposes assertions and retractions when the audit trail itself is the question. An as-of value answers ordinary domain questions at a chosen point in time. The rest of the application keeps using the same functions.

A long-running calculation can also keep one coherent database value while new transactions arrive. If it later commits a proposal, normal optimistic checks still apply. Reasoning about a value and changing durable state remain separate operations.

One library, two storage models

Keep durable domain facts, relationships, and decisions in VevDB. Use the bundled SQLite API for caches, sessions, job state, and derived indexes. One native library gives the application two deliberately different tools.

Where database values change the design

The model matters when an application needs to:

  • preview a change before committing it;
  • run today’s decision logic against historical state;
  • keep one coherent world during long-running work;
  • compare alternative plans using the same rules;
  • navigate connected domain facts without preparing a second object model.

For straightforward current-state rows, SQLite is usually simpler. Distributed coordination belongs to another class of database.

The form factor matters most in software that must remain self-contained: desktop applications, developer tools, on-premises products, and small single-node services. VevDB runs in-process without a JVM or database server. The native SDK downloads for the current release are about 3–4 MB, including the query engine and bundled SQLite storage layer.

The database value is the API

Once the database is a value, past and proposed state stop requiring separate application models. current, asOf(current, t), and with(current, facts) flow through the same functions. The same domain logic can ask each value the same questions, without a separate preview repository or historical read model for that purpose.

Datomic established this programming model. VevDB changes where it can live: inside a native application, as a component small enough to ship with it.
