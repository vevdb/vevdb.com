The Database as a Value

Rich Hickey used this title for his 2012 Datomic talk, which showed how an immutable database value changes the programming model. The same function can reason about the present, the past, or a proposed future. VevDB brings that model to a small native component.

Andreas Flakstad September 15, 2026 6 minute read

This programming model comes from Datomic, not VevDB. In Datomic, a database is an immutable value, and d/with is a pure function that applies transaction data and returns a new database value. VevDB deliberately follows those semantics. Its different bet is the form factor: make them available in a small, in-process native library without a JVM or database server.

Most application code does not receive a database. It receives an ID, a repository, or a connection, and reaches out to storage whenever it needs another fact. That is a practical default. It is also a hidden dependency on one particular world: whatever happens to be in the database at the moment the query runs.

The limitation becomes visible when the application needs to ask a different question. Would this release be valid if we approved these tasks? What did the system know when it made yesterday’s decision? Can we show a preview without first writing temporary state?

Those questions are often answered with separate mechanisms: staging tables, copied objects, audit records, event replay, test doubles, or validation code that operates on a second representation of the domain. Each mechanism can work. The complexity comes from keeping all of them consistent with the current database and with each other.

There is another programming model: make the database itself an immutable value.

One function, several possible worlds

Imagine a release-planning application. Before a release can be published, it must check dependencies, approvals, unresolved risks, and policy rules. The decision can be expressed as an ordinary function whose first argument is a database value:

// Pseudocode. Values in, values out.
function evaluateRelease(db, releaseId):
  blockers = query(db,
    all blockers for releaseId)

  effects = query(db,
    notifications required for releaseId)

  return { blockers, effects }

The function does not open a connection and does not know whether its input represents production, a test fixture, last Tuesday, or a future that may never be committed. It simply asks questions of one stable value.

The imperative part of the program decides which value to provide:

current = database(connection)

proposed = with(current, [
  approve(task: 42),
  assign(task: 57, owner: "Mina")
])

now      = evaluateRelease(current, release: 7)
whatIf   = evaluateRelease(proposed, release: 7)
lastWeek = evaluateRelease(
  asOf(current, "2026-09-08"),
  release: 7
)

with returns a new database value containing the proposed facts. It does not change current, write to storage, or modify the connection. Both values remain queryable, so the application can compare them, inspect entities in either one, run the same policy rules, and discard the proposal when it is finished.

The useful shift is not merely that snapshots exist. It is that current, historical, and hypothetical state share the same data model and query interface. Application functions do not need a separate “preview mode.”

A natural functional core

Functional core / imperative shell is a useful design pattern: keep decisions in deterministic functions and push I/O to the boundary. Databases make that boundary difficult because domain logic commonly queries through a live connection.

An immutable database value moves the boundary. The shell reads the current value, passes it to the core, then performs the returned transaction and effects:

// Functional core
function decide(db, command):
  if not allowed(db, command):
    return rejection

  facts = factsFor(command)
  nextDb = with(db, facts)
  effects = effectsFor(nextDb, command)

  return { facts, effects }

// Imperative shell
db = database(connection)
result = decide(db, command)

transact(connection, result.facts)
send(result.effects)

The core is not limited to a small object graph prepared by the shell. It can query the complete database value, follow relationships, use rules, and derive exactly the view it needs. Yet it still has no authority to change durable state.

Testing follows the same shape. A test creates a database value, passes it to decide, and asserts on returned facts and effects. Testing a regression against old state or a proposed migration does not require a special repository implementation; it requires a different value.

History without a second model

Audit logs often answer “what was written?” while application code needs to answer “what was true?” Reconstructing the second answer can require replay logic or a parallel historical representation.

When earlier database states are themselves database values, the ordinary application query remains useful:

whenApproved = asOf(current, approvalTransaction)

decision = evaluateRelease(
  whenApproved,
  release: 7
)

A history view can expose assertions and retractions when the audit trail itself is the subject of the query. An as-of value answers normal domain questions at a chosen point in time. The application can use both without translating its data into a different historical API.

Concurrency becomes explicit

A database value is stable even while the connection accepts later transactions. That is valuable for long-running calculations and user interfaces: all reads in one operation can share a coherent basis instead of observing a mixture of states.

Stability does not remove concurrency. A hypothetical value can become stale before its facts are transacted. The shell still needs the appropriate domain checks—compare-and-swap, uniqueness constraints, or another form of optimistic validation—when it commits. The advantage is that speculative reasoning and durable mutation are separate, visible steps.

Not every byte belongs in history

Immutable facts are a good fit for durable domain state, relationships, decisions, and information whose provenance matters. They are a poor fit for every cache entry, background-job lease, session, or derived search index.

VevDB therefore exposes the SQLite library already bundled with its durable storage layer. An application can keep domain facts and history in VevDB while using ordinary SQL for operational and ephemeral data. The stores use separate files and transactions do not span both, but the application ships one native library rather than treating one storage model as a universal answer.

Where this model earns its cost

A new database is not justified by architectural elegance alone. Immutable database values become interesting when an application needs more than one of these:

  • queryable history or auditability;
  • previews, planning, validation, or other what-if operations;
  • stable snapshots for long-running work;
  • rich, connected domain data that benefits from Datalog;
  • the same decision logic applied to current, past, and proposed state.

If the application only needs current rows and straightforward lookups, SQLite is likely the simpler choice. If it needs a distributed database service, horizontal scaling, or high-availability coordination, a small embedded component is the wrong category of tool.

The form factor matters most in software that must remain self-contained: desktop applications, developer tools, on-premises products, and small single-node services. VevDB runs in-process without a JVM or database server. The native SDK downloads for the current release are about 3–4 MB, including the query engine and bundled SQLite storage layer.

The database value is the API

Datalog, history, and hypothetical transactions are individually useful. Their combination becomes more powerful when they all operate on the same kind of value. The application can capture one world, create another, and pass either one through the same program.

VevDB inherits this model directly from Datomic: database values, db-with, as-of, history, pull, and Datalog. Its contribution is the deployment shape—a small native component intended to live inside the application.
