Pass the whole database to a function.

Capture an immutable database value and pass it into ordinary application functions. It is a stable snapshot, not a copy of all its data. Each function sees one stable world, can query it freely, and returns data instead of performing I/O.

This makes a functional core and imperative shell a natural fit: decision logic receives db and a command; the shell owns the connection, transactions, and external effects.

Read the article

  • The same function can receive current, historical, or hypothetical state.
  • Tests pass in a database value without giving the core a live connection.
  • Long-running work can keep a stable snapshot while new transactions arrive.

A component you can ship with the application

Embed VevDB in an application and open an in-memory or durable store. The database engine runs inside the application as a small native library.

VevDB fits applications where SQLite would be the natural choice for simple deployment, but the domain benefits from immutable database values, Datalog, queryable history, or hypothetical transactions. Use it from native software or through the Clojure and Java packages.

VevDB focuses on the embedded data model instead of growing into a database platform. That makes it a natural fit for self-contained desktop tools, developer products, on-premises applications, and resource-constrained single-node services.

3–4 MB native SDK downloads in v0.4.0

Embed it through a stable C ABI.

Embed VevDB directly through its stable C ABI or use a language package built on top. The database, query engine, and durable storage all run inside the application process.

The model should feel familiar.

Know Datomic? VevDB follows the same style of semantics: datoms, immutable database values, Datalog, pull, entities, indexes, history, as-of, and db-with. All packaged as a small in-process native library.

See the syntax guide

Not everything belongs in history.

VevDB also exposes the SQLite bundled into its native library, so an application can use both storage models without shipping another database dependency.

Caches, sessions, jobs, email queues, search indexes, and other data that should be updated in place.

The two stores use separate database files. Transactions do not span both stores. Read the SQLite API guide.

The pieces for rich application state

Datalog queries

Query relationships with joins, rules, predicates, aggregates, negation, disjunction, and pull expressions.

Immutable snapshots

Hold and query stable database values while the connection continues accepting transactions.

History and time

Use historical views, as-of, since, and transaction-range reads.

Memory or disk

Open transient in-memory databases or durable stores backed internally by bundled SQLite.

Entity and index access

Use entities, lookup refs, pull, reverse references, range scans, and EAVT/AEVT/AVET/VAET indexes.

Native embedding

Use the stable C ABI directly or through a language package. The query engine and storage run in-process.
